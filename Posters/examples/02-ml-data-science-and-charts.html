Optense — Industry Control System (ICS)

Leveraging Tabular Data for Finding Anomalies Within Industrial Machines

Kemal Dwi Heldy Muhammad

Apple Developer Institute for AIML

Abstract

A single machine could have multiple sensors, relays, actuators, and other instruments that work together to achieve a desired target. Usually, readings from each of these instruments are logged to evaluate how well the machine is performing. Additionally, these logs can be used to detect anomalies by identifying unusual patterns, which may indicate that something is going wrong.

Objectives

ICS is an established system capable of integrating any instrument that uses the Modbus communication protocol. Architecturally, ICS consists of two layers: the controller and the server. The controller layer acts as the core of the system, responsible for controlling and monitoring all connected instruments, while the server layer enables centralized monitoring of multiple controllers across a facility. Given the diversity of supported instruments, two key challenges must be addressed:

  • Training must be done on demand when enough readings have been logged, adapting directly to each machine's operating baseline.

  • Each model must be light enough for an edge device to concurrently run instances of inference in real time to detect anomalies across multiple instruments simultaneously.

Note

Before implementing it on the controller, creating a proof-of-concept on the server could save a lot of time and effort before changing the controller’s architecture.

Creating the Proof-of-Concept

For creating a quick and effortless anomaly detector, building it as an iPad application is the perfect choice for two reasons: Create ML and Core ML. Create ML can train machine learning models and output a compiled model that Core ML runs natively.

27.4°C

Reading #15 — Flagged Anomaly

chiller: OFF

A single reading carries no memory. To judge whether a 27.4°C is suspicious, the model needs to know where the signal has been, how stable it was, how fast it moved, and what time of day it is. These questions can be derived into four features:

Where has it been?

“What’s the recent baseline?”

mean

Average of the last 10 readings. Gives the model a reference point for what "normal" looks like right now, in the current operating state.

How much should it move?

“Stable or volatile movement?”

std

Standard deviation of the same window. A tighter std means the chiller is steady; a wider std means it is actively transitioning.

How fast is it moving?

“Gradual shift or sudden spike?”

delta

Difference from the previous reading. Legitimate changes tend to be gradual. Refrigerant leaks and sensor failures are sudden.

What mode should it be in?

“Normal for this time of day?”

hour

Machines follow human schedules. A chiller runs harder during production hours and idles at night as the model learns its cycle.

On-Device Training and Inference

A gradient boosted tree regressor was chosen for two reasons. First, it handles the non-linear relationships between instrument features without requiring large datasets, which is critical when training happens on demand from a limited reading history. Second, it runs entirely on CPU, making it suitable for edge hardware without a dedicated AI accelerator.

Create ML handles the training side. Given a set of labeled readings, it fits a boosted tree regressor (MLBoostedTreeRegressor) and writes the result as a compiled .mlmodel file. The entire process happens on-device, with no server or cloud dependency.

Core ML handles the inference side. It loads the compiled model and runs predictions in real time, returning a single float per reading. The anomaly score is then computed as the absolute difference between that prediction and the actual sensor value.

The threshold is set at 3 times the training RMSE, meaning the model tolerates normal variation but flags anything significantly outside it.
